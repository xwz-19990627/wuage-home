# wuage-home · 架构（DSH = 家庭智能体中枢）

> 结论：**用 DSH 作为家用智能体中枢（brain）**，wuage-home 仓库是挂在中枢上的“业务内核”
> （记忆与数据层 + 模块 + 技能卡）。不自己造 harness，也不退化成“纯 API 调用”。

## 形态

```
┌──────────────────── DSH（中枢） ────────────────────┐
│ agent 循环 · 工具(bash/fs/web) · 推理模式            │
│ 会话记忆 · 预设(家庭管家…) · 技能卡(wuage-ledger…)  │
│ 任务看板 cron（主动调度）· 插件生态 · Web GUI         │
└──────┬───────────────┬──────────────────┬───────────┘
       │ 技能执行       │ 定时触发          │ 会话入口
       ▼               ▼                  ▼
 wuage 业务内核      数据/事实层       入口适配器
 scripts/ledger.py   data/ledger.db    DSH Web GUI
 web/ 数据视图        → 未来 facts/     （网关/手机已有）
                                     未来 QQ bot 插件
```

- **智能都走中枢**：一句话记账的解析、多轮纠错、周报叙述、未来问答——都由 DSH agent
  （家庭管家预设）在会话内完成，享受 harness 的全部效果（工具、推理、记忆）。
- **事实都进 wuage 数据层**：账本、将来知识库、家庭记忆沉淀在 data/，契约由 wuage 仓库定义。
- **中枢缺什么，wuage 补什么**：DSH 不知道“家庭”是什么——人格预设、领域技能卡、
  数据契约全是 wuage 仓库的。这是互补，不是竞争。

## 为什么 DSH，而不用别的

| 选择 | 结论 |
| --- | --- |
| 自造 harness（LangGraph / Agents SDK…） | 重建轮子：循环/工具/会话/调度全要自己写，不划算 |
| n8n / Dify / Coze | 工作流平台——刻意不用工作流引擎（决策 5）；家庭差异化仍要自己写 |
| Home Assistant | 设备自动化领域，不是 LLM 认知中枢；将来可互补（IoT） |
| 纯 DeepSeek API | 只有“解析”，没有 agent 循环/工具/多轮/记忆——能力天花板低 |
| 本地小模型（Ollama） | 只换模型不换 harness；将来可作中枢的可选 provider |

DSH 优势：本地运行、现成 agent 循环与工具、DeepSeek 官方维护、
**插件机制已验证可改造**（任务看板/SSH/梁神模式 preset 都是插件与预设成果）、
自带 Web GUI 与网关（手机访问基建已有）。

## 可迁移性（重申）

迁移到 NAS = 安装 DSH + 部署 wuage 仓库 + 拷贝 data/ + 配模型密钥 + 装技能/预设。
DSH 本身是可迁移的 node 应用——中枢与业务内核一起搬家，仍然是一套可拷走的体系。

## 改造路径（v0.1.x 起步）

1. 中枢人格与技能：家庭管家预设 ✅ → 后续家人专属预设（member 维度接入时）。
2. 技能卡：wuage-ledger ✅ → 周报、新闻简报、知识问答逐个挂 skill。
3. 主动性：任务看板 cron 定时触发“家庭管家”会话（每日简报/周报/到期提醒）——
   这是中枢从“被动应答”迈向“家庭成员”的关键一步。
4. 入口：DSH Web GUI（现有）→ 公网网关 /ledger/ 面板（v0.1.2 已通）→ QQ bot 插件（v0.4+）。
5. 数据视图：web 面板保持纯数据 UI（查账/图表/改账），不承担智能。

## 风险与对策

- DSH 迭代快、API 变动：wuage 仓库只依赖稳定契约（数据 schema + 技能卡/预设格式），升级只动适配。
- 单账户：家庭多成员靠“多预设 + 会话 + member 字段”渐进支持；权限与隔离到公开入口时再设计。
- API 消耗：会话式智能按次计费，家庭规模很低，可接受；后期可设预算提醒。
## 版本锁定与升级策略（应对 DSH 未稳定）

- 当前中枢版本：**DSH 0.1.0-rc.6**（2026-08-21 记录）。RC 阶段破坏性更新是事实，对策：**钉版本，不追新**。
- **运行快照**：DSH 版本 + wuage 仓库 commit 绑定成一份快照（升级前记录）。
- **升级流程**：看 DSH 变更说明 → 对照下方“接触面”清单评估影响 → 只改适配层 → 冒烟
  （ledger CLI + 面板 API + 一次会话记账通过）→ 更新快照。
- **NAS 迁移 = 快照迁移**：同版本 DSH 安装包 + wuage 仓库同 commit + data/ 拷贝，不要求两边都最新。

## 与 DSH 的接触面（全部薄而可重装）

| 接触面 | 文件 | 破坏性升级时的影响 |
| --- | --- | --- |
| 预设 | presets/wuage-family/（agent.cordis.yml + preset.yml） | 格式随版本微调；persona 内容在仓库，重装即可 |
| 技能卡 | .dsh/skills/wuage-ledger/SKILL.md | 纯 Markdown + frontmatter，格式极稳 |
| 调度 | 任务看板 cron（v0.1.2 起） | 插件维护者适配，我们只消费 |
| 会话入口 | DSH Web GUI / 网关 | DSH 自己维护 |

**业务内核（ledger.py / web.py / SQLite / 模块）零 DSH 依赖**——DSH 怎么改，数据与逻辑不动。

## 迁移成本量化（诚实版）

- 常规破坏性升级（preset/插件格式调整）：适配 + 冒烟 ≈ 0.5～1 天（小版本工作量）。
- 罕见大改（预设/技能机制重写）：重写适配层 ≈ 1～2 天。
- 数据与逻辑丢失风险：**零**（data/ 与 DSH 无关；persona/技能指令都在 wuage 仓库）。
- **逃生舱**：若 DSH 不可持续，把技能卡契约固化为 parse.py + Web 输入框（约 1 个小版本）
  即可脱离 DSH；数据层无需任何改造。永远不把唯一出口赌在 DSH 上。
