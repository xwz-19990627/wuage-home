# 分类体系设计（v0.2 前置 · 待确认）

> 调研结论 + 建议方案。参考：支付宝/随手记（两级大类→小类）、YNAB（Category Group + Category、
> 支持隐藏旧分类）、BudgetApp（扁平 categories 表 + color/icon + 软删除）。

## 成熟方案的共性

1. 主流记账 App 多用**两级**：一级大类（餐饮/交通…）+ 二级小类（外卖/买菜…），统计可下钻。
2. 分类表独立（id 引用），流水只存 id → 改名全局生效、历史不坏。
3. 删除策略普遍是：**已被流水引用的分类禁止物理删除**（YNAB 用"隐藏"，中国系 App 大多"禁止删/移入其他"）。
4. 系统种子分类 + 用户自定义并存；"其他"通常不可删（兜底）。

## 推荐方案：一级分类（预留二级），v1.0 不做两级

| 理由 | 说明 |
| --- | --- |
| AI 从已有分类选择 | 两级让 LLM 输出多一个维度，出错率上升、候选 prompt 变长；当前"优先取已有"策略一级更稳 |
| UI 复杂度 | 级联下拉+两级管理页 vs 一级下拉，移动端一级更轻 |
| 统计闭环 | PRD 阶段一（本月/饼图/7日/账单筛选）一级足够 |
| 未来升级 | categories.parent_id 字段**先预留**（PRD 已有），v0.2 系列开二级=零迁移成本 |

如果你想现在就两级，唯一实质收益是"餐饮里外卖占比"这类下钻统计——建议留到 v1.0 之后按真实使用数据再加。

## 分类规则（v1.0）

**表结构**（对齐 PRD Category + 参考 BudgetApp 的 color）：

```sql
CREATE TABLE categories (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,      -- 分类名（家庭内唯一）
  type        TEXT NOT NULL DEFAULT 'expense',  -- expense | income
  parent_id   INTEGER,                    -- 预留二级（v1.0 恒 NULL）
  is_system   INTEGER NOT NULL DEFAULT 0,-- 1=种子分类
  icon        TEXT,                       -- 可选
  color       TEXT,                       -- 可选（图表用）
  sort_order  INTEGER NOT NULL DEFAULT 0,
  is_archived INTEGER NOT NULL DEFAULT 0 -- 预留（软删/隐藏）
);
```

**种子分类（系统，10 项，全部 expense）**：餐饮、交通、医疗、购物、教育、娱乐、居住、通讯、人情、其他
（存量迁移：医疗健康→医疗；育儿教育→教育；购物/娱乐/居住/交通/餐饮/人情/其他保留；新增"通讯"。

**规则**：
- 新增：手动添加（名称唯一校验）；**大模型不自动建类**（按你拍板，LLM 只从已有类选，匹配不到归"其他"）。
- 改名：允许（id 引用，历史流水跟随显示）。
- 删除：未引用的可删；**已被流水引用 → 禁止删除**（提示"已有 N 笔记录使用了该分类，无法删除，可改名"）。
- 种子分类：可改名/调整排序，但禁止删除（至少"其他"必须保留作兜底）。
- 归档（is_archived）v1.0 先用禁止删除取代，字段预留。
